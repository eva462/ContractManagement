### 一条被记录在案的保留意见

开发方在讨论中明确提出：**「没有业内流程规范，AI 只会胡说八道」**，并建议第一期不做非基础功能。甲方选择先做一版试试。

本设计不推翻这个判断，而是用**按类型的规则模板 + 强制显示依据原文**来对冲它：让用户能看到「AI 依据哪条规则、引用了合同里哪一句」，从而自己判断该不该信。**模板质量决定这个功能的成败**，所以模板必须可编辑、可迭代。

## 2. ⚠️ 涂抹的核心陷阱

### 画黑框 ≠ 涂掉

在 PDF 上盖一个黑色矩形，文字层仍然在下面。复制粘贴、或任何程序读取文本层，内容照样出来。这是文档脱敏领域最经典的事故来源。

### 在本系统里的具体表现

我们的识别流水线有两条路径（见 02 文档 §3）：

| 路径 | 触发条件 | 送给 DeepSeek 的是什么 | 画黑框的后果 |
|---|---|---|---|
| **文本路径** | PDF 有文本层 | **抽出来的纯文字**，根本不渲染图像 | 黑框**完全无效**，金额原样出网 |
| **图像路径** | 扫描件／图片 | 渲染后的 PNG 切块 | 涂黑像素才真的涂掉 |

**所以涂抹必须在两条路径上分别实现，实现方式完全不同：**

- **文本路径** → 按矩形坐标**剔除落在框内的文本行**（mupdf 的 structured text 带每行 bbox，已验证可行）
- **图像路径** → 渲染时把矩形区域**填成纯色**，再切块

### 另一条铁律：原件不动

**涂抹只作用于「送去识别的那一份副本」，存档的 PDF 原件必须完整保留。**

否则归档的合同缺了金额，这个系统的存在意义就没了。涂抹是**出网前的过滤器**，不是对档案的编辑。

```
                 ┌─────────────────────────┐
上传 PDF ────┬──►│ 存档副本（完整，不出网） │──► var/uploads/
             │   └─────────────────────────┘
             │
             │   ┌─────────────────────────┐
             └──►│ 识别副本（按涂抹区剔除） │──► DeepSeek
                 └─────────────────────────┘
```

### 验收要求（写成自动化测试）

**涂抹后送出去的载荷里，被涂区域的文字必须搜不到。** 这条要有测试守着——文本路径尤其容易做成「界面上黑了、实际照发」。

## 3. 涂抹的设计

### 交互

1. 上传 PDF → 前端把每页渲染成预览图
2. 合同管理员在预览图上**拉矩形框**（可多个、可跨页）
3. 提交时把矩形坐标（**归一化成页面宽高的百分比**，避免缩放误差）连同文件一起发给服务端
4. 服务端解析时按坐标过滤，再送 DeepSeek
5. 被涂掉的字段自然识别不到 → 表单留空 → 人工填

### 为什么用矩形而不是选文本

矩形对**两种 PDF 都适用**。选文本只在有文本层时可行，扫描件上没法选——统一用矩形，交互一致，实现也只有一套坐标系。

### 权限

按甲方要求，涂抹权给**合同管理员（MANAGER+）**。经办人上传后可以识别，但涂抹框的绘制和确认由管理员做。

<sub>⚠️ 这条需要确认，见 §5 问题 1 —— 如果经办人不能涂抹，那他就不能自己上传敏感合同去识别，流程上会卡。</sub>

### 留痕

涂抹是「决定什么数据出网」的动作，必须留痕：涂了几个区域、覆盖哪几页、操作人是谁。**不记录被涂掉的内容本身**（记了就等于没涂）。

## 4. 合同风险审查的设计

### 按类型的规则模板

```
review_templates
  id
  contractType   -- 引用 dict_items 里 CONTRACT_TYPE 的 itemCode
  isActive
  updatedAt

review_rules
  id
  templateId
  title          -- 如「付款节奏是否与验收挂钩」
  detail         -- 审查要点的详细描述，直接进提示词
  severity       -- HIGH / MEDIUM / LOW，用于给风险点排序
  sortOrder
```

每个合同类型一套模板。**采购合同看付款节奏和质保，劳务合同看用工合规，数据中心基建合同看耗材和成本口径**——这正是开发方坚持要分模板的理由。

### 规则从哪来

甲方定的路子：**先让 AI 生成初版，人再调**。

所以要有一个「**生成建议规则**」的按钮：管理员选一个合同类型，系统让 DeepSeek 按该类型产出一批候选审查要点，管理员**逐条勾选采纳、编辑措辞**后存成模板。

⚠️ 这里要说清楚：AI 生成的是**候选**，不是权威。没人审过就直接上，就是开发方警告的那个「胡说八道」的场景。所以界面上采纳必须是显式动作，不能默认全选。

### 输出形态

```
风险点
  ├─ 严重度（高/中/低）
  ├─ 命中的规则（哪一条模板规则）
  ├─ 依据原文（合同里的哪一句）  ← 必须有，否则用户没法判断
  └─ 说明与建议
```

**没有「依据原文」的风险点一律丢弃。** 这是防幻觉最有效的一招——模型编不出原文里没有的句子，编了也一眼能看穿。

### 与审批流的关系

风险审查结果**只作为参考显示在详情页和审批界面上，不阻断流转**。

理由：甲方明确说过「你爹公司原本有合同审核人员，目前增加 deepseek 审核环节，只是简化合同条款审核工作，提升效率」。它是给人看的辅助材料，不是关卡。

### 涂抹与风险审查的关系

甲方原话：「涂抹掉的内容不参与 deepseek 的评估，一般脱掉的内容是关于金额类的，也无须审核」。

所以**涂抹后的副本同时用于字段识别和风险审查**，两者共用同一份过滤后的内容。界面上要提示：**本次审查未包含被涂抹的部分**——否则用户会以为 AI 看过全文了。

## 5. 待确认

**问题 1 · 涂抹权限** —— 只有 MANAGER+ 能涂抹的话，STAFF 上传敏感合同就没法自己走识别。要不要放开给经办人（管理员仍可复核）？

**问题 2 · 风险审查的触发时机** —— 三个选择：
- (a) 上传识别时一并做（一次调用，省钱，但草稿阶段合同还没定稿）
- (b) 提交审核时做（内容已定稿，最贴合「辅助审核」的定位）← 推荐
- (c) 详情页手动点「AI 审查」按钮（最灵活，也最可控）

**问题 3 · 第一版模板覆盖哪些合同类型** —— 全部 8 个类型都配，还是先只做贵司最常见的两三个（比如采购、服务、数据中心基建）？后者更实际——模板要靠真实合同调，一次铺 8 个只会 8 个都不准。

## 6. 建议的实施顺序

| 步骤 | 内容 | 理由 |
|---|---|---|
| **1** | 涂抹（两条路径 + 防泄漏测试） | **安全前提**。它决定什么数据能出网，应该先于任何新的出网功能 |
| **2** | 规则模板的表与设置界面 | 风险审查的地基 |
| **3** | 「AI 生成候选规则」+ 人工采纳 | 甲方定的规则来源方式 |
| **4** | 风险审查执行 + 结果展示 | 依赖 1–3 |

步骤 1 不依赖任何待确认项，可以立刻开始。

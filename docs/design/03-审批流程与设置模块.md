本模块做两件互相咬合的事：**把合同的生命周期从「录入即生效」改成真实的审签流程**，以及**把固化在代码里的信息挪到设置里可维护**。

---

## 1. 先说一个必须澄清的语义冲突

需求原文：

> 审核流程走完后，转入线下纸面签署，签署完纸件**归档**，并扫描上传到系统，并**归档**，转入后续的支付流程

这里的「归档」指**纸质原件入档案柜 + 扫描件进系统**，是合同走向生效的一个**中间环节**——之后合同还要履行、还要付款。

但系统现有的 `ARCHIVED`「已归档」是**合同完结、封存、对所有人只读**，是**终点**。

两者同名反义。直接照搬会做出「一归档就不能再付款」的系统。

**本设计的处理**：把两个概念拆成不同的词。

| 概念 | 本设计用词 | 状态码 |
|---|---|---|
| 纸质原件入档 + 扫描件上传 | **归档待办**（生效前的一道关口） | `PENDING_FILING` |
| 合同完结封存、只读 | **已完结** | `CLOSED`（原 `ARCHIVED` 改名） |

## 2. 新的合同生命周期

```
        ┌──────────┐
        │  草稿     │  DRAFT
        │          │  录入中，字段可以不全
        └────┬─────┘
             │ 提交审核（原来的按钮叫「提交生效」）
             ▼
        ┌──────────┐         驳回（带意见）
        │ 待审核    │ ─────────────────────────┐
        │          │  PENDING_APPROVAL         │
        └────┬─────┘  审批流程进行中            │
             │ 审核通过                        │
             ▼                                │
        ┌──────────┐                          │
        │ 待签署    │  PENDING_SIGNING         │
        │          │  转线下纸面签署盖章        │
        └────┬─────┘                          │
             │ 签署完成                        │
             ▼                                │
        ┌──────────┐                          │
        │ 待归档    │  PENDING_FILING          │
        │          │  纸件入档 + 扫描件上传     │
        └────┬─────┘                          │
             │ 归档完成（两个条件都满足才能过）  │
             ▼                                │
        ┌──────────┐                          │
        │ 履行中    │  ACTIVE  ← 支付流程从这里开始
        │          │                          │
        └──┬────┬──┘                          │
           │    │ 提前解除                     │
           │    ▼                             │
           │  ┌──────────┐                    │
           │  │ 已终止    │ TERMINATED         │
           │  └────┬─────┘                    │
           │ 履行完毕   │                      │
           ▼         ▼                        │
        ┌─────────────────┐                   │
        │     已完结       │ CLOSED  ← 只读     │
        │   （原「已归档」）│  ADMIN 可解除      │
        └─────────────────┘                   │
                                              │
        草稿 ◄────────────────────────────────┘
```

### 状态一览

| 状态 | 代码 | 含义 | 可编辑 |
|---|---|---|---|
| 草稿 | `DRAFT` | 录入中 | ✅ 全部字段 |
| 待审核 | `PENDING_APPROVAL` | 审批流程进行中 | ❌ 锁定（要改先撤回） |
| 待签署 | `PENDING_SIGNING` | 审核通过，等线下盖章 | ⚠️ 仅 MANAGER+，且改动会**作废审批结果**重走 |
| 待归档 | `PENDING_FILING` | 已签署，等扫描件和原件入档 | ⚠️ 仅补充归档信息 |
| 履行中 | `ACTIVE` | 正式生效，进入履约与支付 | ⚠️ 仅 MANAGER+ |
| 已终止 | `TERMINATED` | 提前解除 | ⚠️ 仅 MANAGER+ |
| 已完结 | `CLOSED` | 完结封存 | ❌ 只读，ADMIN 可解除 |

### 关键流转规则

| 从 | 到 | 谁 | 校验 |
|---|---|---|---|
| `DRAFT` | `PENDING_APPROVAL` | 经办人本人 / MANAGER+ | 必填字段齐全 |
| `PENDING_APPROVAL` | `PENDING_SIGNING` | 审批人（见 §3） | 全部审批节点通过 |
| `PENDING_APPROVAL` | `DRAFT` | 审批人 | **必填驳回意见** |
| `PENDING_APPROVAL` | `DRAFT` | 经办人本人 | 主动撤回 |
| `PENDING_SIGNING` | `PENDING_FILING` | 经办人 / MANAGER+ | 填签署日期 |
| `PENDING_FILING` | `ACTIVE` | 经办人 / MANAGER+ | **必须同时满足**：至少一个「合同正本」附件 + 填了原件存放位置 |
| `ACTIVE` | `TERMINATED` | MANAGER+ | 必填终止原因和日期 |
| `ACTIVE` / `TERMINATED` | `CLOSED` | MANAGER+ | 二次确认 |
| `CLOSED` | 上一状态 | ADMIN | 二次确认，强制留痕 |
| `DRAFT` | 软删除 | 经办人本人 / MANAGER+ | 仅草稿可删 |

**「待归档 → 履行中」的双条件是这套流程的价值所在**：它用系统把「纸件必须真的归档、扫描件必须真的上传」变成一道过不去的关口，而不是靠人自觉。

### 与现状的差异

| | 现状 | 本设计 |
|---|---|---|
| 状态数 | 4 | 7 |
| 草稿之后 | 直接 `ACTIVE` | 要过审核、签署、归档三关 |
| `ARCHIVED` | 完结封存 | 改名 `CLOSED`，语义不变 |
| 「归档」 | 就是完结 | 拆成 `PENDING_FILING`（入档环节）和 `CLOSED`（完结） |
| 按钮文案 | 保存并提交生效 | **保存并提交审核** |

> 迁移：本地无真实数据，`ARCHIVED → CLOSED` 直接改枚举 + 一条 migration 即可。

## 3. 审批流程

### 待定：审批的形态

这一块**需要你确认**（§5 问题 2），下面是三种常见形态供选：

| 形态 | 说明 | 适合 |
|---|---|---|
| **A. 单级审核** | 提交后由 MANAGER 或指定审批人一个人审 | 5–10 人公司，最省事 |
| **B. 固定两级** | 部门负责人 → 合同管理员，串行 | 有金额风险管控需求 |
| **C. 按金额分级** | 金额 < X 单级；≥ X 加一级；≥ Y 再加一级 | 最贴合实际，但要定金额档位 |

无论哪种，数据模型都一样——用一张 `contract_approvals` 表记每个审批节点：

```
contract_approvals
  id, contractId, seq（第几级）, approverId,
  decision（PENDING / APPROVED / REJECTED）,
  comment（驳回时必填）, decidedAt
```

差别只在**提交时按什么规则生成这些节点**。所以先按 A 做，以后升到 B/C 只改一个「生成审批节点」的函数，不用动数据模型。

### 审批留痕

每次审批动作都写 `audit_logs`，`action` 增加 `APPROVE` / `REJECT` / `WITHDRAW`。摘要形如：

`李四 审核通过（第 1 级），意见：金额与预算相符`

### 4.2 供应商（相对方）管理 —— 字段待确认

这是**把现在的 `counterpartyName` 文本字段升级成独立表**，新建合同时从下拉选择而不是每次手打。

好处：同一家公司不会再出现「XX科技有限公司／XX科技／XX科技（深圳）」三个写法，也能查「跟这家签过多少合同」。

**字段清单需要问财务或合同负责人确认**（§5 问题 3）。我按常见实务先列一版：

| 字段 | 说明 | 必填 |
|---|---|---|
| 单位全称 | 与营业执照一致 | ✅ |
| 统一社会信用代码 | 18 位，开票和合规都要 | ✅ |
| 商业登记证 / 营业执照 | **文件上传**（复用现有附件存储） | |
| 注册地址 | | |
| 联系人 | 可多个 | |
| 联系电话 / 邮箱 | 跟着联系人走 | |
| 开户银行 / 账号 | 付款要用 —— **是否在本系统存，需财务确认** | |
| 纳税人资格 | 一般纳税人 / 小规模 | |
| 备注 | | |

⚠️ 银行账号属于敏感信息。要不要存在这个系统里、谁能看，**必须问过财务**再定。

### 4.3 数据字典 —— 合同类型等不再写死

现在合同类型是代码里的 TS 枚举（采购/销售/服务/租赁/劳务/保密/框架/其他），加一个类型要改代码重新部署。改成数据库表 + 设置页维护。

```
dict_items
  id, dictCode（分组）, itemCode, itemLabel,
  sortOrder, isActive
```

本期纳入的字典分组：

| 分组 | 用途 | 备注 |
|---|---|---|
| `CONTRACT_TYPE` | 合同类型 | **合同编号前缀跟着它走**（采购→CG），所以字典项要带一个前缀字段 |
| `OUR_ENTITY` | 我方签约主体 | 01 模块砍掉的，这次补上 |
| `DEPARTMENT` | 归属部门 | 同上 |

**已被引用的字典项不允许删除，只能停用**（`isActive=false`）——否则历史合同的类型会变成空。停用后新建时选不到，老合同照常显示。

### 单级审核的具体形态

提交审核时生成**一个** `seq=1` 的审批节点，`approverId` 留空表示「任意 MANAGER 及以上均可审」。

这样不用先做审批人配置界面就能跑起来。以后要升级到指定审批人或多级，只改 `createApprovalNodes()` 这一个函数，数据模型和界面都不用动。

**经办人不能审自己提交的合同** —— 即使他是 MANAGER。这条写死在权限判定里。

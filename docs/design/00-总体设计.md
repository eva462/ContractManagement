## 0. 一句话定义

一个公司内部自用的合同台账系统：把纸质/电子合同的关键信息结构化录入，集中管理原件扫描件，全程留痕可追溯；Web 端和手机 App 共用一套后端接口。

---

## 1. 目标与非目标

### 一期目标（M1–M4）

1. 合同信息**录得进去**：字段设计贴合真实合同，不多不少。
2. 合同**找得出来**：台账列表支持关键词、类型、状态、日期区间、经办人筛选。
3. 附件**存得可靠**：扫描件上传、下载、在线预览，文件本身纳入备份。
4. 操作**查得到人**：谁在什么时候改了哪个字段，改成什么，全部可追溯。
5. 手机上**装得上、用得了**：iOS 走 TestFlight，Android 走签名 APK。

### 一期明确不做（留给二期及以后）

| 功能 | 原因 |
|---|---|
| 合同内容 OCR / AI 识别 | 依赖主数据模块先稳定，字段定义先固化 |
| 审批流程（多级会签） | 状态机已预留 `PENDING_APPROVAL`，一期不启用 |
| 到期提醒与推送通知 | 字段 `reminder_days` 一期先存不用 |
| 报表与统计看板 | 数据积累到一定量再做才有意义 |
| 电子签章 / 在线签署 | 涉及第三方 CA，超出内部系统范围 |
| 多租户 / 组织隔离 | 单公司自用，不需要 |
| 对接钉钉/企微/SSO | 一期本地账号密码即可 |

> 原则：一期宁可少做，也要把**数据模型和审计**打对。后面加功能是往上叠，改数据模型是往下刨。

## 2. 技术方案

### 2.1 推荐结论

```
┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐
│   Web 浏览器     │   │   iOS App       │   │  Android App    │
│                 │   │  (Capacitor)    │   │  (Capacitor)    │
└────────┬────────┘   └────────┬────────┘   └────────┬────────┘
         │                     │                     │
         └─────────────────────┼─────────────────────┘
                               │  HTTPS / REST (JSON)
                               │  Bearer Token
                    ┌──────────▼──────────┐
                    │   API 服务 (Node)    │
                    │  Fastify + Prisma   │
                    └──────────┬──────────┘
                               │
                 ┌─────────────┴─────────────┐
                 │                           │
        ┌────────▼────────┐        ┌─────────▼────────┐
        │   PostgreSQL    │        │  附件存储 (磁盘)  │
        │   (Docker)      │        │  + 每日备份       │
        └─────────────────┘        └──────────────────┘
```

| 层 | 选型 | 说明 |
|---|---|---|
| 前端 | Vite + React 19 + TypeScript | 纯 SPA，构建产物既能当网页部署，也能被 Capacitor 打进 App 壳 |
| UI | Tailwind CSS + shadcn/ui | 组件可直接改源码，不受第三方库版本绑架；表格密集型界面表现好 |
| 移动端 | **Capacitor 7** | 把上面的 Web 构建产物包成原生 App，UI 代码 100% 复用；相机拍合同、文件选择、生物识别、推送都有官方插件 |
| 后端 | Fastify + TypeScript | 轻量、快、TS 支持好；比 NestJS 少一层抽象，5-10 人的系统不需要 NestJS 的重量 |
| ORM | **Prisma** | schema 即文档，迁移可追溯，类型安全；后续加字段有正规 migration 记录 |
| 数据库 | **PostgreSQL 16** | 见 2.5 |
| 校验/契约 | **Zod**（放在 `packages/shared`） | 前后端共用同一份 schema，接口契约不会漂移 |
| 认证 | JWT（access 2h + refresh 30d） | 见 2.4 |

### 2.2 为什么不选另外两条路

**为什么不用 Next.js 全栈？**
Next.js 的强项（SSR、Server Actions、RSC）在打包成 App 时全部用不上——Capacitor 需要的是纯静态构建产物，Next.js 一旦 `output: export`，Server Actions 和大部分服务端能力就废了，等于绕一大圈回到 SPA。既然终局是 App，不如一开始就用 Vite 做纯 SPA，路径最短、坑最少。

**为什么不用 React Native / Expo？**
原生体验确实更好，但代价是 Web 端要么另写一套，要么用 `react-native-web` 妥协。合同台账是典型的"表格 + 表单 + 文件"界面，这类界面 WebView 完全够用，RN 的性能优势体现不出来，而开发成本会翻倍。5-10 人的内部系统不值得。

**Capacitor 的代价是什么？（诚实说明）**
App 本质是一个 WebView 壳。滚动惯性、键盘弹起、长列表性能会比原生略差一点点；重度动画不适合。对合同管理这类业务系统，这些差距用户基本感知不到。换来的是：**一次开发，Web/iOS/Android 三端同步，后续每加一个模块只写一遍。**

### 2.3 ⚠️ iOS 分发的现实约束（这是唯一有硬门槛的地方）

你说的"直接信任并安装"，在 iOS 上只有四条路：

| 方式 | 年费 | 可行性 | 说明 |
|---|---|---|---|
| **TestFlight** ✅ **推荐** | $99/年 | ✅ 可行 | 同事装个 TestFlight App，输入邀请码即可安装，系统完全信任、无任何警告。内部测试员上限 100 人，你只有 5-10 人绰绰有余。**代价：每个构建包 90 天过期，需要重新上传一次；首次上传要过 Apple 一轮简单审核（通常 1-2 天）** |
| Ad Hoc 分发 | $99/年 | ⚠️ 麻烦 | 需要逐台收集设备 UDID（上限 100 台），描述文件 1 年过期，换手机要重新打包。不推荐 |
| Apple Developer **Enterprise** Program | $299/年 | ❌ **拿不到** | 可以完全绕开 App Store 无限内部分发，但 Apple 硬性要求**公司 100 名以上员工** + D-U-N-S 编号。5-10 人的公司不符合资格 |
| 上架 App Store | $99/年 | ❌ 不合适 | 内部系统上公开商店会被 Apple 以"仅限特定人群使用"为由拒审 |

**结论：iOS 走 TestFlight，需要一个 $99/年的 Apple Developer Program 账号（公司或个人均可）。这是唯一现实可行的路径。**

Android 简单得多：用自己的密钥库签名打 APK，直接发给同事安装即可（首次需在系统里允许一次"安装未知来源应用"）。如果想去掉这个提示，可以花 $25 一次性开通 Google Play 开发者账号，走"内部测试"轨道分发。

### 2.4 App 带来的两个设计影响（现在就要定，不然后面返工）

**① 认证必须用 Token，不能用 Cookie Session**
Capacitor 的 WebView 里，App 页面来自 `capacitor://localhost`，而 API 在 `https://你的域名`，属于跨域。iOS 的 ITP 会对跨站 Cookie 做严格限制，Session Cookie 方案在 App 里会踩坑。
→ 统一用 **JWT Bearer Token**：Web 端存 `localStorage`，App 端存 Capacitor `Preferences`（iOS 落到 Keychain）。Access Token 2 小时，Refresh Token 30 天，接口层统一自动续期。

**② 服务器必须有真域名 + 受信任的 HTTPS 证书**
iOS 的 ATS（App Transport Security）强制要求 HTTPS，**自签名证书在 TestFlight 分发的 App 里会被直接拒绝连接**，且无法通过"信任此证书"绕过。
→ 需要：一个域名（例如 `contract.你公司.com`）+ Let's Encrypt 免费证书。如果服务器在公司内网没有公网 IP，用 **Cloudflare Tunnel** 是最省事的方案（免费，自动配证书，不用开放端口）。

### 2.5 数据库：PostgreSQL（确认可行）

先直接回答你的顾虑：**Postgres 与 App 部署没有任何冲突。** App 是纯 HTTPS 客户端，数据库只跑在服务器上，两者物理隔离。

选 Postgres 而非 SQLite/MySQL 的理由，都指向你说的"数据稳定性很重要"：

- **事务与约束最严格**：合同金额、状态流转、审计日志写入必须在同一事务里，Postgres 的 MVCC 和外键约束是这类场景的成熟答案。
- **`DECIMAL(18,2)` 精确金额**：绝不用浮点存钱。
- **JSONB 存审计差异**：审计日志的字段级 before/after 用 JSONB 存，既灵活又能索引查询。SQLite 做不到，MySQL 的 JSON 支持弱一截。
- **中文全文检索**：合同名称、对方单位的模糊搜索，Postgres 的 `pg_trgm` 扩展表现很好。
- **备份成熟**：`pg_dump` 逻辑备份 + WAL 归档，恢复演练路径清晰。

SQLite 的问题是并发写入会锁库、复杂查询弱，而且以后想换库要重做 schema——为了省一次 `docker compose up` 而埋一个迁移债，不划算。

### 2.6 部署形态

```yaml
# docker-compose.yml 概要
services:
  db:        # postgres:16-alpine，数据挂 named volume
  api:       # Node 服务，挂载 uploads/ 目录
  web:       # Caddy 静态托管前端 + 反向代理 /api → api（Caddy 自动申请 HTTPS 证书）
  backup:    # 每日 pg_dump + 附件目录打包，保留 30 天
```

一条 `docker compose up -d` 起全套。服务器要求极低：2 核 4G 足够跑 5-10 人。

## 3. 一期 MVP 范围

第一条可运行的业务闭环，共 5 个能力：

1. **手工录入合同** — 新建表单，字段分组（基础信息 / 相对方 / 金额结算 / 日期期限 / 内部管理），必填校验，合同编号自动生成或手填查重。
2. **合同台账** — 分页列表，支持关键词搜索（合同名称/编号/对方单位）、多条件筛选（类型/状态/经办人/签订日期区间/金额区间）、排序、列表导出 Excel。
3. **详情 / 编辑** — 详情页展示全部字段 + 附件区 + 操作留痕时间线；编辑走同一套表单；状态流转按钮独立于编辑。
4. **附件管理** — 上传（PDF/JPG/PNG/DOCX/XLSX，单文件 ≤50MB，单合同 ≤20 个）、分类标注（合同正本/补充协议/附件/其他）、在线预览（PDF 和图片）、下载、删除。手机端支持**直接拍照上传合同扫描件**。
5. **操作留痕** — 所有写操作自动记录，详情页时间线可读展示（如"张三 于 2026-08-27 14:30 将合同金额从 ¥100,000.00 修改为 ¥120,000.00"）。

## 4. 角色与权限

5-10 人的内部系统，权限保持极简——**4 个固定角色，不做权限矩阵配置页**（真需要了二期再加）。

| 角色 | 代码 | 权限 |
|---|---|---|
| 系统管理员 | `ADMIN` | 全部权限 + 用户管理 + 字典维护 + 物理删除 + 解除归档 |
| 合同管理员 | `MANAGER` | 查看/编辑**全部**合同、状态流转、归档、导出、删除（软删） |
| 经办人 | `STAFF` | 创建合同、编辑**自己经办**的合同、查看全部合同、上传附件 |
| 只读用户 | `VIEWER` | 仅查看合同、下载附件 |

**默认可见范围：全员可见全部合同。** 内部小团队，合同信息共享的价值大于隔离。若你希望 `STAFF` 只能看自己经办的，我在实现时留一个全局开关 `CONTRACT_VISIBILITY = ALL | OWN`，改配置即可切换（第 13 节待你确认）。

**权限落地方式**：后端每个接口用统一的 `requireRole()` + `requireOwnership()` 中间件，前端只负责隐藏按钮（**前端隐藏不算权限，后端必须再校验一次**）。

## 5. 合同状态流转

### 一期状态机

```
                    ┌──────────────────────────────┐
                    │                              │
              ┌─────▼─────┐    提交生效        ┌────┴─────┐
      新建 ──►│   DRAFT   │───────────────────►│  ACTIVE  │
              │   草稿    │  (校验必填字段)     │  履行中   │
              └─────┬─────┘                    └──┬───┬───┘
                    │                             │   │
                    │ 删除(软删)                   │   │ 手动终止
                    ▼                   到期日已过 │   │ (填终止原因+日期)
              ┌──────────┐             (定时任务)  │   │
              │ 已删除    │                       │   │
              └──────────┘              ┌─────────▼┐  │
                                        │ EXPIRED  │  │
                                        │ 已到期    │  │
                                        └────┬─────┘  │
                                             │        │
                                        ┌────▼────────▼───┐
                                        │   TERMINATED    │
                                        │    已终止        │
                                        └────────┬────────┘
                                                 │
                    ACTIVE / EXPIRED / TERMINATED│ 归档
                                        ┌────────▼────────┐
                                        │    ARCHIVED     │  ◄── 归档后只读
                                        │     已归档       │      (仅 ADMIN 可解除)
                                        └─────────────────┘
```

| 状态 | 代码 | 含义 | 可编辑 |
|---|---|---|---|
| 草稿 | `DRAFT` | 录入中，信息可能不全 | ✅ 全部字段 |
| 履行中 | `ACTIVE` | 已签署生效，正在执行 | ✅ 除编号外可改（每次改留痕） |
| 已到期 | `EXPIRED` | 到期日已过（系统每日自动判定） | ⚠️ 仅 MANAGER+ |
| 已终止 | `TERMINATED` | 提前解除/终止 | ⚠️ 仅 MANAGER+ |
| 已归档 | `ARCHIVED` | 完结封存 | ❌ 只读 |
| *待审批* | *`PENDING_APPROVAL`* | *二期审批流启用，一期预留不用* | — |

**流转规则**：

| 从 | 到 | 触发 | 权限 | 附加要求 |
|---|---|---|---|---|
| DRAFT | ACTIVE | 手动"提交生效" | STAFF+（本人）/ MANAGER+ | 校验全部必填字段 |
| ACTIVE | EXPIRED | **系统自动**（每日 02:00 定时任务，`expiry_date < 今天` 且非长期有效） | 系统 | 审计日志记为系统操作 |
| ACTIVE | TERMINATED | 手动"终止合同" | MANAGER+ | 必填终止原因 + 终止日期 |
| ACTIVE / EXPIRED / TERMINATED | ARCHIVED | 手动"归档" | MANAGER+ | 二次确认弹窗 |
| ARCHIVED | 上一状态 | 手动"解除归档" | ADMIN | 二次确认 + 强制留痕 |
| DRAFT | （软删除） | 手动"删除" | 本人 / MANAGER+ | 仅 DRAFT 可删；其他状态只能归档 |

**关键约束：非 DRAFT 状态的合同永远不允许删除，只能归档。** 这是合同系统的底线。

## 6. 合同字段字典

`*` = 必填（提交生效时校验，草稿态可留空）

### 6.1 基础信息

| 字段 | 代码 | 类型 | 说明 |
|---|---|---|---|
| 合同编号 * | `contract_no` | string(64) | **全局唯一**。支持自动生成或手工填写（自动查重） |
| 合同名称 * | `title` | string(255) | |
| 合同类型 * | `contract_type` | 字典 | 采购 / 销售 / 服务 / 租赁 / 劳务 / 保密(NDA) / 框架 / 其他 |
| 业务分类 | `category` | 字典 | 可选，自定义二级分类 |
| 我方主体 * | `our_entity` | 字典 | 公司签约主体（多主体公司用） |
| 合同简述 | `description` | text | 一句话说明合同内容 |

### 6.2 相对方（对方单位）

| 字段 | 代码 | 类型 | 说明 |
|---|---|---|---|
| 对方单位 * | `counterparty_id` | 关联 | 关联 `counterparties` 表，支持下拉选择 + 快速新建 |
| 对方联系人 | `counterparty_contact` | string(64) | 冗余存在合同上（联系人可能因合同而异） |
| 对方联系电话 | `counterparty_phone` | string(32) | |
| 对方邮箱 | `counterparty_email` | string(128) | |

> `counterparties` 表独立存放：单位名称、统一社会信用代码、地址、默认联系人、备注。**做成独立表而非文本字段**，避免同一家公司在系统里出现"XX科技有限公司/XX科技/XX科技（深圳）"三个写法，以后想统计"跟这家公司签了多少合同"直接能查。

### 6.3 金额与结算

| 字段 | 代码 | 类型 | 说明 |
|---|---|---|---|
| 金额类型 * | `amount_type` | enum | `TAX_INCLUDED` 含税 / `TAX_EXCLUDED` 不含税 / `NO_AMOUNT` 无金额（如 NDA） |
| 合同金额 | `amount` | **DECIMAL(18,2)** | `amount_type = NO_AMOUNT` 时不填 |
| 币种 | `currency` | enum | CNY(默认) / USD / EUR / HKD |
| 税率(%) | `tax_rate` | DECIMAL(5,2) | 如 6.00、13.00 |
| 付款/结算方式 | `payment_terms` | text | 如"预付30%，验收后付60%，质保金10%满12个月付清" |
| 是否含质保金 | `has_warranty_deposit` | boolean | |

### 6.4 日期与期限

| 字段 | 代码 | 类型 | 说明 |
|---|---|---|---|
| 签订日期 * | `sign_date` | date | |
| 生效日期 * | `effective_date` | date | |
| 到期日期 | `expiry_date` | date | `is_perpetual = true` 时不填 |
| 长期有效 | `is_perpetual` | boolean | 如 NDA、框架协议 |
| 续签方式 | `renewal_type` | enum | 不续签 / 自动续签 / 到期协商 |
| 到期提醒提前天数 | `reminder_days` | int | 默认 30。**一期只存不用，二期做提醒** |
| 终止日期 | `terminated_at` | date | 状态转 TERMINATED 时必填 |
| 终止原因 | `termination_reason` | text | 状态转 TERMINATED 时必填 |

### 6.5 内部管理

| 字段 | 代码 | 类型 | 说明 |
|---|---|---|---|
| 经办人 * | `owner_id` | 关联 users | 默认当前登录用户 |
| 归属部门 | `department` | 字典 | 可选 |
| 签署方式 | `signing_method` | enum | 纸质盖章 / 电子签 / 双方盖章 |
| 纸质原件存放位置 | `original_location` | string(255) | 如"行政部档案柜 A-03" |
| 原件份数 | `original_count` | int | |
| 状态 * | `status` | enum | 见第 5 节 |
| 备注 | `remark` | text | |

### 6.6 系统字段（不在表单上）

`id` (UUID) · `parent_contract_id`（**预留**，指向主合同，用于二期的补充协议） · `created_by` · `created_at` · `updated_by` · `updated_at` · `deleted_at`（软删除）

### 6.7 合同编号生成规则（待确认，见第 13 节）

推荐格式：`{类型缩写}-{年份}-{4位流水}`，例如：

- 采购合同 → `CG-2026-0001`
- 销售合同 → `XS-2026-0007`
- 服务合同 → `FW-2026-0012`

流水号按「类型 + 年份」维度独立自增，每年归零。新建表单上提供「自动生成」按钮，也允许手工覆盖（提交时校验唯一性）。

## 7. 数据模型


**索引规划**（5-10 人量级不会有性能问题，但正确的索引是习惯）：

- `contracts`: `contract_no` UNIQUE、`status`、`owner_id`、`counterparty_id`、`sign_date`、`expiry_date`、`deleted_at`
- `contracts`: `title` 和 `contract_no` 建 GIN + `pg_trgm` 索引（中文模糊搜索）
- `audit_logs`: `(entity_type, entity_id, created_at DESC)` 联合索引
- `contract_attachments`: `contract_id`、`sha256`

**软删除**：`contracts` 用 `deleted_at`，所有查询默认过滤。物理删除仅 ADMIN 可执行，且必须先归档。

## 8. 审计规则

审计是这个系统的核心价值之一，规则定死：

### 8.1 记什么

| 维度 | 字段 | 说明 |
|---|---|---|
| 谁 | `user_id` + `user_name`（**快照**） | 存快照，用户改名或离职删号后历史记录依然可读 |
| 何时 | `created_at` | 带时区的 `timestamptz` |
| 对什么 | `entity_type` + `entity_id` | CONTRACT / ATTACHMENT / COUNTERPARTY / USER / DICT |
| 做了什么 | `action` | CREATE / UPDATE / DELETE / STATUS_CHANGE / UPLOAD / DOWNLOAD / EXPORT / LOGIN / LOGIN_FAILED |
| 改了什么 | `changes` (JSONB) | 字段级 before/after 差异，仅记录**实际发生变化**的字段 |
| 人话摘要 | `summary` | 生成可读文本，前端时间线直接显示 |
| 来源 | `ip` + `user_agent` | 区分 Web / iOS / Android 来源 |

`changes` 示例：

```json
{
  "amount":     { "before": "100000.00", "after": "120000.00" },
  "expiry_date":{ "before": "2026-12-31", "after": "2027-06-30" }
}
```

`summary` 示例：`张三 将合同金额从 ¥100,000.00 修改为 ¥120,000.00，到期日期从 2026-12-31 修改为 2027-06-30`

### 8.2 铁律

1. **写操作与审计日志必须在同一数据库事务内**——业务成功但日志丢失，等于没有审计。
2. **审计日志只增不改不删**：应用层不提供任何 UPDATE/DELETE 接口，数据库层用独立角色权限 + 触发器双重兜底。
3. **附件下载也要记录**：合同是敏感资料，谁下载过必须留痕。
4. **登录成功和失败都记录**：失败记录用于发现异常尝试。
5. **系统自动操作（如定时任务置为已到期）也记录**，`user_name` 记为 `系统`。

### 8.3 展示

合同详情页底部「操作留痕」时间线，倒序展示，支持展开查看字段级差异。ADMIN 另有全局审计日志查询页（按人/按时间/按操作类型筛选）。

## 9. 接口设计

统一前缀 `/api/v1`，REST 风格，全部返回 JSON。

**接口契约由 `packages/shared` 里的 Zod schema 单一定义**：后端用它做运行时入参校验，前端从它推导 TypeScript 类型。这样即使前后端在同一个工程里，接口边界依然是**显式、独立、有强制约束**的——改了字段，前端会立刻编译报错，不会等到运行时才发现。

### 认证
```
POST   /auth/login              账号密码登录 → { accessToken, refreshToken, user }
POST   /auth/refresh            刷新 access token
POST   /auth/logout             登出（服务端吊销 refresh token）
GET    /auth/me                 当前用户信息与权限
POST   /auth/change-password    修改密码
```

### 合同
```
GET    /contracts               台账列表（分页/搜索/筛选/排序）
POST   /contracts               新建（默认 DRAFT）
GET    /contracts/:id           详情（含附件列表、相对方、经办人）
PATCH  /contracts/:id           编辑（局部更新，自动 diff 生成审计）
DELETE /contracts/:id           软删除（仅 DRAFT）
POST   /contracts/:id/status    状态流转 { to, reason?, terminatedAt? }
GET    /contracts/:id/audit-logs 该合同的操作留痕
GET    /contracts/export        导出 Excel（沿用列表筛选条件）
GET    /contracts/next-no       按类型+年份生成下一个合同编号
```

### 附件
```
POST   /contracts/:id/attachments   上传（multipart，服务端校验类型/大小/算 sha256）
GET    /attachments/:id             元信息
GET    /attachments/:id/download    下载（**鉴权后由服务端流式返回，绝不暴露静态目录**）
GET    /attachments/:id/preview     预览（PDF/图片，内联返回）
DELETE /attachments/:id             删除
```

### 相对方 / 字典 / 用户
```
GET    /counterparties          列表（支持搜索，用于表单下拉）
POST   /counterparties          新建（表单内快速新建）
PATCH  /counterparties/:id

GET    /dicts/:code/items       取字典项（contract_type / our_entity / department / category）
POST   /dicts/:code/items       ADMIN
PATCH  /dicts/:code/items/:id   ADMIN

GET    /users                   ADMIN / MANAGER（经办人下拉也用它）
POST   /users                   ADMIN
PATCH  /users/:id               ADMIN
POST   /users/:id/reset-password ADMIN
```

### 统一响应格式
```jsonc
// 成功
{ "data": { ... }, "meta": { "page": 1, "pageSize": 20, "total": 137 } }
// 失败
{ "error": { "code": "CONTRACT_NO_DUPLICATED", "message": "合同编号已存在", "field": "contract_no" } }
```

## 11. 数据稳定性与备份

你说"数据稳定性很重要"，一期就把这套做完，不留到出事之后：

| 措施 | 做法 |
|---|---|
| **数据库持久化** | Postgres 数据挂 Docker named volume，不放容器内 |
| **每日自动备份** | 每日 03:00 `pg_dump -Fc` 全量备份，保留 30 天滚动 |
| **附件一起备份** | `uploads/` 目录同步打包（**只备份数据库、丢了附件 = 合同扫描件全没**，这是最常见的疏漏） |
| **异地副本** | 备份文件自动同步一份到云盘/对象存储（rclone），本机损坏时还有救 |
| **恢复演练** | 提供 `scripts/restore.sh`，并在 M1 阶段**实际演练一次恢复**，确认备份真的能用 |
| **软删除** | 合同永不物理删除，误删可恢复 |
| **审计日志** | 任何数据变化可追溯到人和时间，可人工回滚 |
| **附件去重与校验** | 上传时算 SHA-256，既去重也可校验文件是否损坏 |
| **数据库约束** | 外键、唯一约束、CHECK 约束都在数据库层加，不只靠应用层——应用有 bug 时数据库是最后一道防线 |

## 13. 待你拍板的 6 件事

在开始写 M1 之前，这几项需要你确认：

**① 技术栈是否按第 2 节推荐方案？**
Vite + React + TypeScript（前端）· Fastify + Prisma（后端）· PostgreSQL · Capacitor（打包 App）· 单仓库 npm workspaces。

**② iOS 分发：是否接受 $99/年的 Apple Developer Program + TestFlight？**
如果暂时不想花这笔钱，我们可以先只做 Web + Android APK，iOS 留到需要时再接（Capacitor 的好处是届时接入成本很低，代码不用改）。

**③ 服务器部署在哪？能否提供域名 + HTTPS？**
- 云主机（阿里云/腾讯云轻量服务器，约 ¥100/月）——最省事
- 公司内网机器 + Cloudflare Tunnel（免费，无需公网 IP）
- 其他

⚠️ 提醒：**iOS App 强制要求受信任的 HTTPS 证书，自签证书不可用。**

**④ 合同编号：自动生成还是手工填写？**
推荐自动生成 `CG-2026-0001` 格式（类型缩写-年份-流水），同时允许手工覆盖。如果你公司已有编号规则，告诉我格式，我按你的来。

**⑤ 合同可见范围：全员可见，还是经办人 + 管理员可见？**
默认建议全员可见（内部小团队信息共享价值更大），我会预留开关随时可切。

**⑥ 初始字典数据，请提供：**
- **我方主体**：贵公司的签约主体全称（可能不止一个）
- **合同类型**：默认给「采购 / 销售 / 服务 / 租赁 / 劳务 / 保密 / 框架 / 其他」，需要增删请说
- **部门**：如果有部门划分，列一下
- **初始用户**：需要开哪几个账号、各是什么角色

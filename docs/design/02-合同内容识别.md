# 02 · 合同内容识别（上传即预填）

| 项目 | 内容 |
|---|---|
| 模式 | 本地开发；识别调用 DeepSeek API（合同内容会出网到 DeepSeek） |
| 闭环 | 上传合同文件 → 自动识别字段 → 预填录入表单 → **人工逐项核对** → 保存 |
| 上游 | [`01-合同主数据模块.md`](01-合同主数据模块.md) |
| 日期 | 2026-08-28 |

---

## 1. 一句话

把「对着合同一个字段一个字段敲」变成「传一份合同扫描件，系统填好，人核对一遍」。

**识别结果永远不直接入库。** 合同系统里一个错的金额或日期的代价，远高于省下的录入时间。

---

## 2. 引擎与关键约束

用户选定 **DeepSeek API**，另接了**通义千问**作为对比项（两家可用 EXTRACTION_PROVIDER 切换，见 README）。以下是 DeepSeek 查证后的硬约束（2026-08-28 官方文档）：

| 约束 | 事实 | 对策 |
|---|---|---|
| 输入格式 | **不接收 PDF**，只接收 JPEG / PNG / GIF / WebP | PDF 在本地先转（见 §3） |
| 图片分辨率 | 自动缩到约 **800×800**，每张封顶 **384 token** | A4 整页会糊掉小字 → **每页切 2×2 块**分别送，有效分辨率 ×4 |
| 每请求图片数 | 最多 600 张 | 切块后一份 10 页合同 = 40 张，远未触顶 |
| JSON 输出 | 只有 `response_format: {type:'json_object'}`，**不支持传 schema 强制** | 返回值用 `packages/shared` 现成的 Zod schema 校验，失败重试（最多 2 次） |
| 已知缺陷 | 官方注明「偶尔返回空 content」 | 空返回按失败处理，走重试 |

### 模型与成本

| 用途 | 模型 | 单价（输入/输出，每百万 token） |
|---|---|---|
| 文本抽字段 | `deepseek-v4-pro` | $0.66–1.32 / $1.98–3.96 |
| 图片抽字段 | `deepseek-v4-flash-vision-exp` | $0.22–0.44 / $0.66–1.32 |

<sub>低价为非高峰（UTC 周一至周五 01:00–04:00、06:00–10:00 之外）。</sub>

单份成本估算：电子版 PDF 约 1 万 token ≈ **¥0.02**；5 页扫描件切成 20 张图 ≈ 7.7K token ≈ **¥0.02**。一年几百份合同，识别费用在 **¥10 以内**，可以忽略。

> ⚠️ **合同原件会上传到 DeepSeek 服务器进行识别。** 这是选定该引擎的直接后果，写在这里以免以后被当成意外。不想出网的合同，走原来的手工录入即可（识别是可选入口，不是必经步骤）。

---

## 3. 两段式流水线

刻意拆成两段，因为这两段的可替换性完全不同：**第一段永远在本地、不出网**，第二段才是可换的 AI 供应商。

```
        上传文件（PDF / JPG / PNG）
                  │
    ┌─────────────▼──────────────┐
    │ ① DocumentLoader（本地）    │   不出网。纯本地解析。
    │                            │
    │  PDF 有文本层 → 抽文本      │   → 文本路径（准、便宜）
    │  PDF 无文本层 → 渲染成图片   │   → 图片路径
    │  图片 → 切 2×2 块           │
    └─────────────┬──────────────┘
                  │
    ┌─────────────▼──────────────┐
    │ ② FieldExtractor（DeepSeek）│   ★ 第四个可替换边界
    │                            │
    │  文本 → deepseek-v4-pro     │
    │  图片 → …-vision-exp        │
    └─────────────┬──────────────┘
                  │
    ┌─────────────▼──────────────┐
    │ ③ Zod 校验 + 重试（本地）    │   复用 ContractWriteSchema
    └─────────────┬──────────────┘
                  │
    ┌─────────────▼──────────────┐
    │ ④ 预填表单 → 人工核对 → 保存 │   ★ 不可跳过
    └────────────────────────────┘
```

**怎么判断 PDF 是电子版还是扫描件**：抽出的文本层字符数 ÷ 页数 < 50 就当扫描件走图片路径。阈值放常量里可调。

---

## 4. 识别哪些字段

19 个字段里，**能从合同正文读出来的 13 个**参与识别：

| 识别 | 字段 |
|---|---|
| ✅ | `contractNo` `title` `contractType` `counterpartyName` `counterpartyContact` `amountType` `amount` `currency` `paymentTerms` `signDate` `effectiveDate` `expiryDate` `isPerpetual` |
| ❌ 不识别 | `ownerId`（系统内部，默认当前用户）· `status`（永远从草稿开始）· `originalLocation`（纸质存放位置，合同里没有）· `remark`（人写的） |

### 每个字段带置信度

模型对每个字段同时给出 `confidence: high | medium | low` 和 `evidence`（原文出处片段）。前端：

- `low` → 黄色高亮 + 「请重点核对」
- 没识别出来 → 留空，不猜
- 鼠标悬停看 `evidence`，知道这个值是从合同哪句话来的

---

## 5. 交互

**入口**：新建合同页顶部一个「上传合同自动识别」区域（也支持拖拽）。

1. 选文件 → 立刻显示「正在识别…」（识别一份约 5–15 秒）
2. 识别完 → 字段自动填进表单，低置信度的黄色高亮
3. 顶部提示条：`已识别 9 个字段，其中 2 项置信度较低，请核对后保存`
4. 用户逐项核对、改错、补齐
5. 保存时走**和手工录入完全相同**的校验和接口
6. **上传的原文件自动存为该合同的附件（分类：合同正本）**，不用再传一次

**识别失败**（网络错、key 无效、模型返回不可用）→ 提示一句，表单保持可手工填，不阻断录入。

---

## 6. 留痕

识别是对数据的一次实质影响，必须可追溯：

- 识别动作本身记一条 `EXTRACT` 留痕：用了哪个模型、几页、耗时、识别出几个字段
- 合同创建后的 `CREATE` 留痕里标注「由 AI 识别预填，经 XXX 核对」
- **不记录合同全文到留痕**（太长且敏感），只记文件名和哈希

---

## 7. 可替换边界（第四个）

| 边界 | 接口 | 当前实现 | 以后可换成 |
|---|---|---|---|
| **字段识别** | apps/server/src/extraction/provider.ts | OpenAiCompatibleExtractor，已接 DeepSeek 与通义千问 | 智谱 / 本地模型 / 其他 OpenAI 兼容服务 |

装配点仍是 `apps/server/src/context.ts`。**`DocumentLoader`（PDF 解析、切块）不在这个边界内**——它永远本地执行，换 AI 供应商时不受影响。

没配 `DEEPSEEK_API_KEY` 时装配一个 `NullExtractor`：接口照常返回，`available: false`，前端不显示识别入口。**没有 key 也能正常跑整个系统**，只是没有识别功能。

## 8. 验收标准

### A. 环境
- [ ] 没配 `DEEPSEEK_API_KEY` 时系统正常启动，新建页不显示识别入口，手工录入不受影响
- [ ] 配了 key 后识别入口出现

### B. 文档解析（本地，不出网）
- [ ] 电子版 PDF 走文本路径，不产生任何图片
- [ ] 扫描件 PDF 走图片路径，每页切成 4 块
- [ ] 直传 JPG/PNG 走图片路径
- [ ] 加密 PDF / 损坏文件 → 明确报错，不崩

### C. 字段识别
- [ ] 13 个字段能识别，另 4 个不参与
- [ ] 返回值经 Zod 校验；不合规时自动重试，两次仍失败则报错
- [ ] 日期一律归一成 `YYYY-MM-DD`；金额去掉千分位和「元」「¥」，保留两位小数
- [ ] 中文大写金额（壹拾贰万元整）能正确转成数字
- [ ] 识别不出的字段留空，不编造

### D. 预填与核对
- [ ] 识别结果填进表单后，仍能手工改任意字段
- [ ] 低置信度字段黄色高亮，可看到 `evidence` 原文出处
- [ ] 顶部显示「已识别 N 个字段，M 项需重点核对」
- [ ] 保存走与手工录入完全相同的校验
- [ ] 原文件自动成为该合同的附件（合同正本），不需要二次上传

### E. 失败与边界
- [ ] key 无效 → 提示「识别服务不可用」，表单可继续手工填
- [ ] 超时（>60s）→ 中止并提示，不卡死界面
- [ ] 传一份不是合同的文件（如随手拍的风景照）→ 返回几乎全空，不硬凑

### F. 留痕
- [ ] 识别动作产生 `EXTRACT` 记录，含模型名、页数、耗时、识别字段数
- [ ] 留痕里不出现合同全文

## 9. 真实调用实测（2026-08-28）

用脚本生成的两份已知答案样本合同（`npm run sample`），真实调用 DeepSeek 验证（`npm run verify:live`）。
样本里刻意埋了几个坑：甲方是我方、乙方是对方；金额只给中文大写；签订日期写成「二〇二六年三月十二日」。

| 路径 | 模型 | 耗时 | 结果 |
|---|---|---|---|
| 电子版 PDF（文本层） | `deepseek-v4-pro` | 40s 上下 | **11/11 全对** |
| 扫描件 PDF（4 张切图） | `deepseek-v4-flash-vision-exp` | 10–27s | **11/11 全对** |

三个关键点都通过：甲乙方没填反、中文大写金额转对、中文数字日期转对。两条路径都是**零错值**。

### 过程中发现的一个坑

第一轮只有 73%（8/11），漏掉了对方联系人、生效日期、到期日期——而这三项在原文里写得很清楚。

原因是**提示词里的 JSON 示例被模型当成了字段白名单**：示例里出现过的字段它才输出。
改成「先用表格列全 13 个字段并标注常见位置 + 明说示例只是演示格式」之后，两条路径都升到 100%。

> 以后往识别里加字段，**字段表和示例两处都要改**，只改一处会静默漏识别。

---

## 10. 不做

- 不做合同条款风险审查（那是另一个模块）
- 不做多份合同批量识别（先跑通单份）
- 不做识别结果的自动入库（永远要人核对）
- 不做 Word(.docx) —— 本期只做 PDF 和图片，用户已确认
